# Sub-Phase 2.1: Multi-Tenancy, Supabase RLS & RBAC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement database-level Row Level Security (RLS) policies across all 19 domain tables in Supabase PostgreSQL, create 5-tier RBAC authorization middleware in FastAPI, configure Supabase S3 storage bucket policies, and verify 100% security coverage using the `supashield` CLI.

**Architecture:** 
1. Alembic migration (`002_multi_tenancy_rls.py`) enabling `ALTER TABLE <name> ENABLE ROW LEVEL SECURITY` and applying tenant isolation policies using `(auth.jwt() -> 'app_metadata' ->> 'organization_id')::uuid`.
2. Server-side FastAPI RBAC authorization middleware (`apps/api/app/core/rbac.py`) enforcing role permissions (`Admin`, `Claims Manager`, `Claims Operator`, `Senior Approver`, `Finance`).
3. Automated Supashield CLI verification sequence (init, audit, lint, test --as-user, test-storage, coverage) + TDD cross-tenant Pytest verification.

**Tech Stack:** Python 3.11/3.14, FastAPI, SQLAlchemy, Alembic, Supabase Cloud PostgreSQL, Supashield CLI.

---

## Global Constraints

- RLS policies must cover all 19 domain tables (direct `organization_id` or parent-inherited joins).
- `supashield` CLI must run all 6 verification steps against Supabase and produce 100% clean output.
- Hand-tested cross-tenant Pytest query (`Broker A` reads `Broker B`) must return exactly `0` rows.
